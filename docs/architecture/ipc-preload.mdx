# IPC & preload

## The bridge

`electron/preload/index.js` exposes a single namespace — `window.electronAPI` — through `contextBridge.exposeInMainWorld`. The renderer never touches Node directly: `contextIsolation: true`, `nodeIntegration: false`, `sandbox` on.

The preload groups ~250 functions into sections: file ops, dialogs, tabs, clipboard, search, history, tests, debugger, run engine, Git, terminal, AI, opencode, browser, extensions, Chrome extensions, Android, QEMU, notebook, updater, ports, dev tunnels, zoom, session, canvas, project hub/storage, MCP/mise, live edit — plus event subscriptions.

Event listeners are **whitelisted** (`onMenuEvent` valid-channels list is pinned by a regression test — `tests/menu-channels.test.cjs`), so main can never push arbitrary channels into the renderer.

## Registration

Handlers register via `ipcMain.handle` (and `ipcMain.on` for synchronous clipboard/native-drag). `ipc-invoke.js` wraps registration and keeps a handler map so the **MCP server** can call any channel directly with a synthetic sender — with a blocklist of interactive/UI channels (`dialog:*`, `contextMenu:show`, `menu:*`, `tab:contextMenu`, `ext:popupAnchor`, …).

The full channel list is in [reference/ipc-channels.md](../reference/ipc-channels.md).

## Main → renderer events

The main process pushes state changes as `webContents.send` events: `fs:change`, `output:log`, `terminal:data`, `run:data`/`run:exit`, `git:clone:log`, `test:event`, `debug:event`, `android:progress`, `qemu:progress`, `devtunnels:event`, `ext:*`, `updater:*`, `settings:updated`, `zoom:changed`, `editor:openFile`, menu actions (~50 channels), and more.

## Custom protocols

| Scheme | Privileges | Purpose |
|---|---|---|
| `ibx-file` | standard, secure, fetch, CORS, stream | Serves preview files / extension panels with a MIME map and referrer-based CORS |
| `idiotbox` | standard, secure, fetch | Internal pages (`idiotbox://extensions/`) and deep links (`idiotbox://update`) |
| `crx://` | via electron-chrome-extensions | Chrome extension resources |

## Webview bridges

- `browser:registerGuest` + `browser-registry.js` track every `<webview>` guest.
- The design inspector speaks CDP (`browser:pickComponent`, `browser:guestEdit`) with the guest's debugger.
- Extension webview panels use a `__ibxHost` postMessage bridge generated by the scaffold.

## Conventions

- Channels are namespaced by domain (`git:`, `fs:`, `terminal:`, `android:`, …).
- Long outputs are capped in main (e.g. MCP `MAX_OUTPUT 8000`).
- Slow operations return promises; progress flows through dedicated event channels.
